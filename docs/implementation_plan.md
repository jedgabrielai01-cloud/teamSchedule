# Implementation Plan

## Overview

Full-stack calendar application with an embedded AI assistant. FastAPI backend serves a
NextJS frontend as static files. Data lives in a single SQLite file. The AI assistant
reads from and writes to the database based on natural language instructions.

## Phase 2 — Database Layer

### Step 2.1 — SQLite schema

Four tables are created on first boot via `db.py`:

**`users`**
```
id            INTEGER PRIMARY KEY AUTOINCREMENT
username      TEXT NOT NULL UNIQUE
password_hash TEXT NOT NULL
```
Seeded from the union of all names in `leave_records.csv` and `support_schedule.csv`.
Default password `RSD` is hashed with bcrypt at seed time.

**`leaves`**
```
id            INTEGER PRIMARY KEY AUTOINCREMENT
employee_name TEXT NOT NULL
leave_date    DATE NOT NULL
leave_type    TEXT
```
Seeded from `data/leave_insert.sql`.

**`public_holidays`**
```
id            INTEGER PRIMARY KEY AUTOINCREMENT
holiday_date  DATE NOT NULL
description   TEXT
location      TEXT
```
Seeded from `data/leave_insert.sql` (holidays section).

**`support_schedule`**
```
id               INTEGER PRIMARY KEY AUTOINCREMENT
schedule_date    DATE NOT NULL
primary_oncall   TEXT
secondary_oncall TEXT
backup_oncall    TEXT
onshore_oncall   TEXT
comments         TEXT
```
Seeded from `data/schedule_insert.sql`.

### Step 2.2 — `db.py`

Responsibilities:
- Open a SQLite connection with `PRAGMA journal_mode=WAL` (allows concurrent reads
  during writes).
- On first boot (DB file does not exist): create all tables, run both seed SQL files,
  insert all users with hashed passwords.
- Expose a `get_db()` FastAPI dependency that yields a connection and closes it after
  the request.

Seeding is skipped entirely if the `.db` file already exists. To reseed: delete the
`.db` file and restart.

## Phase 3 — Authentication

### Step 3.1 — `auth.py`

- `hash_password(plain: str) -> str` — bcrypt hash via passlib.
- `verify_password(plain: str, hashed: str) -> bool`
- `create_token(username: str) -> str` — signs a JWT with `sub=username`, expiry 8
  hours, using `JWT_SECRET` from `.env`.
- `decode_token(token: str) -> str` — returns username or raises 401.
- `get_current_user` — FastAPI dependency that reads the `Authorization: Bearer ...`
  header, decodes the token, and returns the username string. Used on every protected
  route.

### Step 3.2 — `routers/auth.py`

**`POST /auth/login`**
- Body: `{ username, password }`
- Looks up user in `users` table.
- Verifies password hash.
- Returns `{ token: "..." }` on success, 401 on failure.

## Phase 4 — Backend API Routers

All routes except `/auth/login` require the `get_current_user` dependency.

### Step 4.1 — `routers/calendar.py`

**`GET /api/calendar?month=YYYY-MM`**

Returns a single JSON object with all data needed to render one calendar month:
```json
{
  "leaves": [...],
  "schedule": [...],
  "holidays": [...]
}
```
Filters each table by the requested month range. This is the only endpoint the
frontend polls. Polling interval: 5 seconds.

### Step 4.2 — `routers/leaves.py`

**`POST /api/leaves`**
- Body: `{ leave_date, leave_type? }`
- `employee_name` is always set to `current_user` — users can only add their own
  leaves.
- Validation: check `support_schedule` for `primary_oncall = current_user` on
  `leave_date`. If match found, reject with 409 and a descriptive message.
- Insert into `leaves`.

**`PUT /api/leaves/{id}`**
- Body: `{ leave_date?, leave_type? }`
- Fetch the record. If `employee_name != current_user`, return 403.
- Run the same Primary Support validation on the new date if date is changing.
- Update the record.

**`DELETE /api/leaves/{id}`**
- Fetch the record. If `employee_name != current_user`, return 403.
- Delete the record.

### Step 4.3 — `routers/schedule.py`

**`PUT /api/schedule/{schedule_date}`**
- Body: `{ primary_oncall }`
- Only `primary_oncall` is updated. All other columns are untouched.
- Any authenticated user may call this.
- Returns the updated row.

No POST or DELETE — the schedule rows are fixed; only the person assigned can change.

### Step 4.4 — `routers/holidays.py`

**`POST /api/holidays`**
- Body: `{ holiday_date, description?, location? }`
- Any authenticated user may insert.

**`PUT /api/holidays/{id}`**
- Body: `{ holiday_date?, description?, location? }`
- Any authenticated user may update.

**`DELETE /api/holidays/{id}`**
- Any authenticated user may delete.

## Phase 5 — AI Assistant

### Step 5.1 — Conversation state

Each user session maintains an in-memory conversation history (list of
`{role, content}` dicts) stored in a Python dict keyed by username on the FastAPI
process. History is cleared on logout or server restart. This is sufficient given the
single-container deployment.

### Step 5.2 — System prompt

Built dynamically on each request. Contains:

1. Today's date and the logged-in username.
2. The rules from AGENTS.md (scope, ownership, primary support block, etc.).
3. A snapshot of current data relevant to the conversation (last 60 days of leaves,
   schedule, and holidays) injected as structured text.
4. Instructions for the response format (see Step 5.3).

### Step 5.3 — Response format

The model is instructed to always respond with valid JSON:

```json
{
  "response": "Human-readable reply shown to the user.",
  "action": null
}
```

When a confirmed action is needed:

```json
{
  "response": "Done. I've added your leave for August 16.",
  "action": {
    "type": "insert_leave | update_leave | delete_leave | update_primary_support | insert_holiday | update_holiday | delete_holiday",
    "data": { ... }
  }
}
```

When asking for confirmation (action not yet executed):

```json
{
  "response": "I'll add August 16 as your vacation leave. Confirm? (yes / no)",
  "action": null
}
```

The pending action is held in conversation history. On a "yes" reply, the AI emits the
action JSON. On "no", it cancels.

### Step 5.4 — `routers/ai.py`

**`POST /api/ai/chat`**
- Body: `{ message: string }`
- Appends `message` to conversation history as `role: user`.
- Builds system prompt with current data snapshot.
- Calls OpenRouter (`nvidia/nemotron-3-nano-30b-a3b:free`) via `httpx`.
- Parses the JSON response.
- If `action` is non-null:
  - Validates the action against the rules (ownership, primary support conflict,
    allowed operations).
  - Executes the appropriate DB operation internally (reuses the same logic as the
    REST routers).
  - Appends the assistant reply to history.
- Returns `{ response: string }` to the frontend.

**`DELETE /api/ai/history`**
- Clears the conversation history for the current user.

## Phase 6 — Frontend

### Step 6.1 — Auth token management

- On successful login, store the JWT in `localStorage` as `token`.
- All API calls include `Authorization: Bearer <token>` header via a shared `fetch`
  wrapper.
- On any 401 response, clear the token and redirect to `/login`.

### Step 6.2 — `app/login/page.tsx`

- Centered card with the gradient color palette from AGENTS.md.
- Username and password fields.
- `POST /auth/login` on submit.
- On success: save token, redirect to `/calendar`.
- On failure: show inline error message.

### Step 6.3 — `app/calendar/page.tsx`

- On mount: redirect to `/login` if no token.
- Maintains `currentMonth` state (default: today's month).
- Fetches `GET /api/calendar?month=YYYY-MM` on mount and every 5 seconds via
  `setInterval`.
- Renders `<Calendar>` with the fetched data and `<AIPanel>` side by side.
- Prev / Next month navigation buttons update `currentMonth` and trigger an immediate
  re-fetch.

### Step 6.4 — `components/Calendar.tsx`

- Receives `{ leaves, schedule, holidays }` as props.
- Renders a 7-column grid (Sun → Sat).
- Prepends empty cells for the day-of-week offset of the first of the month.
- Renders one `<DayBox>` per calendar day.

### Step 6.5 — `components/DayBox.tsx`

- Fixed height (e.g. `min-h-32`), no overflow clipping — content never collapses the
  box.
- Sections rendered in order (skipped entirely if no data for that section):
  1. Primary support
  2. Secondary support
  3. Backup on-call
  4. Onshore on-call
  5. Persons on leave (one line per person)
  6. Holiday label (description or generic "Holiday")
- Each section uses a small colored label consistent with the gradient palette.
- Boxes that fall outside the current month are greyed out.

### Step 6.6 — `components/AIPanel.tsx`

- Fixed-height scrollable chat window.
- Message input at the bottom.
- `POST /api/ai/chat` on submit; appends both user message and assistant response to
  the local chat history.
- A "Clear chat" button calls `DELETE /api/ai/history`.
- No client-side streaming — waits for the full response before displaying it.

## Phase 7 — Docker & Scripts

### Step 7.1 — `Dockerfile`

Two-stage build:

**Stage 1 — Build NextJS**
```
FROM node:22-alpine AS frontend-builder
WORKDIR /app/frontend
COPY frontend/package*.json ./
RUN npm ci
COPY frontend/ ./
RUN npm run build
```

**Stage 2 — FastAPI runtime**
```
FROM python:3.13-slim
WORKDIR /app
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
COPY backend/pyproject.toml ./
RUN uv sync --no-dev
COPY backend/ ./backend/
COPY data/ ./data/
COPY --from=frontend-builder /app/frontend/out ./frontend/out
EXPOSE 8000
CMD ["uv", "run", "uvicorn", "backend.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

FastAPI serves the NextJS static export from `/` using `StaticFiles`.

### Step 7.2 — `docker-compose.yml`

```yaml
services:
  app:
    build: .
    ports:
      - "8000:8000"
    env_file: .env
    volumes:
      - ./db:/app/db     # persists schedule.db across container restarts
```

### Step 7.3 — Start / Stop scripts

Each script simply runs `docker compose up -d` (start) or `docker compose down` (stop).
Provided for Mac (`.sh`), Linux (`.sh`), and Windows (`.bat`).

## Key Constraints Summary

| Constraint | Enforced by |
|---|---|
| Leave blocked when Primary Support on that date | `routers/leaves.py` + `routers/ai.py` |
| Users can only modify their own leaves | `routers/leaves.py` (ownership check) + AI validation |
| Primary_oncall is the only updatable schedule field | `routers/schedule.py` (PUT only, fixed columns) |
| Any user can update any primary support | No ownership check on schedule route |
| Any user can manage holidays | No ownership check on holidays route |
| All users see the full calendar | `/api/calendar` returns complete data |
| JWT required on all routes except `/auth/login` | `get_current_user` dependency |
| SQLite WAL mode | `PRAGMA journal_mode=WAL` in `db.py` |
| Seed runs only once | DB file existence check in `db.py` |
